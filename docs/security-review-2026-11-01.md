# Аудит безопасности и конкурентной целостности — 01.11.2026

**Проверенная ветка:** `feature/editorial-atelier-v2`, draft PR №5. Это обзор исходников Cloudflare Worker/D1, Mini App, SQL-триггеров и GitHub Actions, а не внешний пентест работающего сервиса.

**Среда испытаний:** Node.js + SQLite в памяти с реальными SQL-схемой и миграциями, фиктивные Telegram initData, изолированный поддельный ответ Bot API. Попытки нарушить доступность настоящего Cloudflare-бота **не предпринимались**. В рабочем демо нет реальных денег и продаж.

## Модель угроз и границы доверия

1. **Публичный посетитель** может обращаться к `/app`, `/api/catalog`, `/health`, `/media/product/ID`. Он не должен получать личные или администраторские записи.
2. **Авторизованный покупатель** доказывает Telegram ID через подписанный `initData`. Его корзина, заявки и контактные данные должны изолироваться от других покупателей.
3. **Администратор** может менять ассортимент, сметы, остатки, статусы и вручную фиксировать финансовые поступления/возвраты; даже добросовестный администратор может нажать кнопку дважды или запустить два параллельных запроса.
4. **Cloudflare D1** гарантирует атомарность отдельной SQL-команды и пакета `DB.batch`, но запросы и чтения **за пределами** пакета могут наблюдать разные состояния. Поэтому `SELECT → вычисление → UPDATE` не равнозначно атомарному изменению.
5. **Telegram Bot API** может быть временно недоступен после успешной фиксации заказа в D1. Уведомление и сохранение данных — две разные операции.

## Воспроизведённые и исправленные проблемы

| Приоритет | Подсистема | Исходная ошибка | Механизм исправления / тест |
|---|---|---|---|
| P1 | Оформление в Mini App и Telegram | Одновременное изменение корзины после чтения списка позволяло потерять добавленную позицию при оформлении | Состояние **всей корзины** и снимки цены/себестоимости проверяются непосредственно внутри атомарного списания. При расхождении весь D1 batch откатывается; корзина сохраняется |
| P1 | Корзина Mini App | Два параллельных добавления могли записать количество `1` вместо `2` | Атомарный `INSERT … ON CONFLICT DO UPDATE quantity=quantity+1`; удаление — условные `UPDATE`/`DELETE` |
| P1 | Ручной журнал финансов | Два конкурентных возврата могли оба пройти предварительную проверку и создать отрицательный баланс | Проверка суммарных поступлений и статуса заказа **внутри одной SQL INSERT**; второй возврат отклоняется |
| P1 | Команда `/forgetme` | Контактные поля очищались, но положительный Telegram ID продолжал связывать пользователя с закрытыми заказами | После проверки незавершённых заказов Telegram ID заменяется уникальным внутренним отрицательным идентификатором; удаляются старые `checkout_requests`, корзина, сессия, фото-референсы, контактные данные |
| P1 | Неуспешное оформление | После отката D1 batch в базе оставался «фантомный» отменённый заказ с контактами покупателя | Условное удаление пустой записи заказа при откате, без затрагивания реально зафиксированных позиций и ключей повтора; тест подтверждает отсутствие лишних заказов |
| P2 | Excel `/report` | Итоговое количество заказов и сумма поступлений считались **только по последним 1000 строкам**, давая недостоверные итоги | SQL-агрегаты по полной истории; ограничение 1000 строк в таблицах деталей явно обозначено в XLSX и подписи |
| P2 | Мини-приложение | Архивный товар мог стать неустранимым из корзины / оформление могло пропустить архивную позицию | Можно удалить архивную позицию, но нельзя повторно добавить или оформить частичный заказ; показывается `available=0` |
| P2 | Административная сводка | Метрики рассчитывались только по ограниченным спискам заказов и платежей | Непагинированные SQL-агрегаты по полной истории |
| P2 | `/health` | Отвечал `database:true` лишь по наличию binding, не проверяя D1 | Отдельный `SELECT 1`; при ошибке D1 HTTP 503 |

**Подтверждение:** до исправления отрицательные тесты **реально падали** при параллельной работе, после исправления те же сценарии проходят. Проверка на одном запросе не является доказательством устранения гонки.

## Положительные защитные механизмы, проверенные по коду

- `verifyTelegramInitData`: HMAC-SHA256 на основе BOT_TOKEN, одна подпись, защита от старого `auth_date` (600 секунд), допустимые поля, сравнение байтов без преждевременного выхода.
- Администраторский allowlist проверяется **после** проверки подписи; запросы на личные API без валидного `initData` не получают доступ.
- Режим реальных продаж открывается только при **одновременном** `DEMO_MODE=0` и `STORE_READY=1`. На текущем опубликованном демо эти параметры не переключались.
- Для отмены заказов используется SQL-триггер и отдельное подтверждение физического возврата после отправки; двойной акт предотвращает UNIQUE constraint.
- HTML динамически экранируется, XLSX хранит клиентские строки как `inlineStr` и не исполняет формулы. CSP блокирует inline-JS и сторонние фреймы.
- В webhook проверяется отдельный Telegram secret header; обработанные update ID защищены уникальностью записи.
- Тестовый каталог и Chrome QA не подключаются к живой D1; пользовательские секреты не входят в коммиты.

## Открытые риски (не объявлять исправленными)

| Приоритет | Открытый вопрос | Почему важен и критерий закрытия |
|---|---|---|
| P2 | **Зависимость отката от успешной очистки записи заказа** | Нормальный отказ D1 batch теперь удаляет «фантомную» запись и проверен тестом. Если после неуспешной транзакции **сама D1 станет недоступна**, очистка тоже может не завершиться. Перед боевой эксплуатацией предпочтительна единая транзакция создания заголовка и позиций; требуется chaos-test разрыва связи с D1 |
| P1 | **Отсутствие подтверждённых лимитов на публичное чтение и медиа** | Публичные маршруты запрашивают D1, а получение фото может обращаться к Telegram API. Нет подтверждения Cloudflare rate limiting/cache на реальном аккаунте. Следует настроить ограничения и кэширование, тестировать **локально** (не нагрузочным тестом на живом бесплатном тарифе) |
| P1 | **Резервные копии и восстановление D1** | Есть краткосрочный Time Travel, но нет подтверждённой независимой переносимой копии и учебной проверки восстановления |
| P2 | **Уведомления после фиксации заказа** | При сбое Telegram Bot API после успешного SQL-коммита пользователь может не получить подтверждение; повтор webhook не гарантирует повторную отправку после удаления FSM-сессии. Нужны надёжная доставка (outbox/retry) и тест отказа Bot API |
| P2 | **Неполный список заказов/платежей в Excel и админке** | Итоговые суммы исправлены, но детали по-прежнему ограничены последними 1000 записями, админка — 100. Для настоящего бизнеса потребуется пагинация и полный экспорт |
| P2 | **Политика удаления/хранения** | `/forgetme` удаляет связь с Telegram ID в текущей базе, но не гарантирует удаления старых внешних бэкапов, исторических Telegram-сообщений и ручных банковских идентификаторов. Необходима правовая процедура |
| P2 | **Не пройдена реальная мобильная приёмка** | Headless Chrome и синтетический Telegram initData — не настоящий Telegram WebView на iOS/Android; полное оформление со второго реального аккаунта не проверено |

Приоритет P1 отражает бизнес-критичность до включения реальных продаж, **не** утверждение, что сейчас доступна эксплуатация без Telegram-авторизации. Демо продолжает ограничивать операции покупателя.

## План следующего цикла исследования

1. В отдельном изолированном D1-тесте проверить отказ **самого подключения к базе после неуспешного batch** и возможность очистки временной записи; переход к полностью атомарному созданию заказа предпочтительнее зависимого отката.
2. Проверить сбой Bot API после успешного коммита: idempotency, восстанавливаемая доставка уведомлений, статусы повторных webhook.
3. Провести fault-injection на конкурентные изменения корзины, статусов, оплаты и возвратов через один независимый сценарий.
4. Выполнить статическую проверку распространения чувствительных данных (`telegram_id`, `contact_phone`, `custom_measurements`, `BOT_TOKEN`) и сроков хранения.
5. Проверить документированное восстановление D1 на **отдельной тестовой базе** без воздействия на опубликованное демо.

**Граница готовности:** все найденные и исправленные проблемы прошли автономные unit/integration tests; полная эксплуатационная безопасность реальных платежей, резервных копий и мобильного Telegram **не доказана**. PR №5 остаётся draft и не развернут в действующий Worker.

## Дополнение: безопасный откат временного заказа

Добавлен негативный тест, доказавший, что после сбоя оформления у старого кода сохранялся заказ без товарных позиций и с контактными данными. В обоих каналах (Mini App и бот) теперь применяется условное удаление **только** пустого `status='new'` заказа, для которого нет зафиксированных позиций; Mini App также проверяет отсутствие ключа идемпотентности. Сработавший D1 batch никогда не удаляется этим путём. В тестовой среде ошибка воспроизведена до исправления и устранена; пример: [успешный прогон Node](https://github.com/Ai-b0ss/atelier-telegram-shop/actions/runs/41292919870).

**Остающийся риск:** удаление временной записи выполняется отдельным SQL-запросом после отката. При одновременном отказе подключения очистка может не пройти. Для полной защиты в промышленной среде создание заголовка заказа и все связанные изменения должны быть в одном D1 batch; данная архитектурная задача остаётся открытой.
