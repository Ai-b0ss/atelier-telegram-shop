# Защита main от непроверенных изменений (issue #15)

**Статус на 1 ноября 2026:** CI запускается, но GitHub репозиторий пока **не имеет активного Ruleset**. Это не новый сбой Node-тестов, а известный риск управления релизами. Готовая конфигурация находится в [`.github/main-ruleset.json`](../.github/main-ruleset.json).

## Проверенные факты

- GitHub позволяет создать Ruleset для **публичного репозитория даже на GitHub Free**. Для создания нужен доступ администратора к репозиторию. [Правила GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
- REST API для записи Ruleset требует `Administration: write`; подключённый к ChatGPT GitHub App не имеет этого права и возвращает 403. Это ограничение **прав доступа**, а не ошибка синтаксиса правил. [GitHub REST](https://docs.github.com/en/rest/repos/rules?apiVersion=2022-11-28#create-a-repository-ruleset).
- В репозитории `Ai-b0ss/atelier-telegram-shop` по публичному API список Ruleset на момент аудита был пуст.
- Ночной мониторинг сообщил об этом как о «новом P1» повторно, хотя риск был зарегистрирован в issue №15 ранее. Уведомление исправлено: известная незакрытая проблема не должна повторно публиковаться как новый инцидент.

## Что гарантирует предлагаемое правило

Область: **только `refs/heads/main`**. Включено:

1. Все изменения должны поступать через pull request (0 обязательных одобрений для автономной работы, но обсуждения должны быть разрешены).
2. Обязательно должны проходить все семь постоянно доступных check contexts: `Seeded state-machine / mutation detection`, `Full Node regression and fault injection`, `pytest (3.11)`, `pytest (3.12)`, `pytest (3.13)`, `CodeQL / javascript-typescript`, `CodeQL / python`.
3. Проверки должны быть актуальны относительно свежего `main` (`strict_required_status_checks_policy=true`), что помогает поймать конфликт между двумя отдельно зелёными PR.
4. Запрещены force push и удаление `main`. В конфигурации нет bypass actors.

**Почему не требуем визуальную и Cloudflare-проверки как обязательные:** существующие `visual-qa.yml` и `cloudflare-worker.yml` используют `paths:` фильтры. Для PR только с документацией их jobs не запускаются; требование несуществующего статуса заблокировало бы PR навсегда. Эти проверки продолжают запускаться на изменениях релевантных файлов. Автоматические unit-тесты проверяют, что все семь требуемых contexts запускаются для каждого PR без фильтра путей.

## Как активировать без копирования токенов в чат

Если GitHub CLI `gh` на локальном компьютере уже авторизован **под владельцем репозитория**, выполните из корня клона проекта:

```bash
gh api --method POST repos/Ai-b0ss/atelier-telegram-shop/rulesets --input .github/main-ruleset.json
python scripts/main_ruleset.py --check
```

Это одноразовое изменение настроек GitHub. Если нужен собственный fine-grained token, выдавайте его **только** для данного репозитория с разрешением `Administration: write`, храните локально и **никогда не передавайте в чат или файл репозитория**. Альтернативная установка из локальной среды:

```bash
python scripts/main_ruleset.py --plan
# GH_TOKEN уже безопасно определён в окружении.
python scripts/main_ruleset.py --apply
python scripts/main_ruleset.py --check
```

`--apply` **ничего не меняет**, если одноимённый Ruleset уже существует, но его содержимое отличается: скрипт отказывает и требует ручного разбора вместо рискованной перезаписи. `--check` использует только публичный GitHub API, валидирует реальное состояние правила и возвращает ненулевой код при отсутствии защиты; `--plan` не выполняет сетевых запросов.

Можно также открыть [Settings → Rules → Rulesets](https://github.com/Ai-b0ss/atelier-telegram-shop/settings/rules) и создать правило по приложенной конфигурации. Если пользователь не обладает правами владельца, его должен применить администратор.

## Проверка после применения

1. `python scripts/main_ruleset.py --check` → `PASS`; список API показывает `enforcement: active`. Только успешный POST **недостаточен**, нужна проверка GET после создания.
2. Создать отдельный *безопасный тестовый PR* с намеренно проваленной проверкой на тестовом файле. GitHub должен **запретить** merge; не нужно намеренно изменять действующий Worker.
3. Исправить тест на том же PR, дождаться всех обязательных checks, убедиться, что merge разрешается. Закрыть тестовый PR без объединения.
4. Подтвердить, что без правилом предусмотренного обхода нельзя напрямую писать в `main` или использовать force push. **Не пробовать разрушительный force push** ради испытания.
5. Только после этих проверок закрыть [issue №15](https://github.com/Ai-b0ss/atelier-telegram-shop/issues/15).

## Границы защиты

Ruleset не отменяет возможность ошибиться в требованиях, тестовой модели и собственных правах администраторов. Даже семь зелёных checks не доказывают отсутствие уязвимостей. Продолжать раздельные Cloudflare D1 backup/restore, fault-injection, мобильную WebView-приёмку, CodeQL и изолированные генеративные тесты. Не включать `STORE_READY` и не менять существующую боевую D1 без самостоятельной приёмки.
