**Worker:** https://atelier-customwear-demo-2026.igorekglukhovskii43.workers.dev/health
**Telegram:** https://t.me/atelier_customwear_2611_bot

## Состояние — 1 ноября 2026

Telegram webhook установлен через официальный Bot API и указывает на этот Worker.
Три секретные переменные `BOT_TOKEN`, `ADMIN_IDS`, `WEBHOOK_SECRET`

После переключения:

- `/report` отправил настоящий XLSX в Telegram (проверено в клиенте);

Бот работает **без включённого компьютера**, в пределах лимитов бесплатного
тарифа Cloudflare Workers + D1. В Cloudflare хранится отдельная база, не
синхронизированная с локальной SQLite.

## Реализация

- Worker `src/index.js` принимает POST `/webhook` с проверкой
  `X-Telegram-Bot-Api-Secret-Token` и ведёт историю `update_id` в D1.
- Cloudflare D1: `atelier-customwear-demo-2026`, схема `schema.sql`.
- `seed.sql` добавляет 3 категории, 3 вымышленных изделия, 4 варианта.
- Демонстрационный режим `DEMO_MODE=1`: только администратор может создать
  тестовый заказ. Посторонним клиентам реальные продажи недоступны.
- Поддерживаются каталог, корзина, заявка на пошив, версии смет,
  статусы, ручной учёт поступлений и Excel.
- `src/xlsx.js` формирует корректный XLSX без внешних runtime-зависимостей.

## Автоматическое подключение без раскрытия токенов

В каталоге проекта есть:
- `scripts/sync-cloudflare-secrets.py` — читает локальный `.env`, генерирует
  webhook-секрет при отсутствии, проверяет формат значений, посылает JSON
  только в stdin официального Wrangler, проверяет только названия переменных.
- `scripts/cutover-cloudflare.py` — проверяет Worker и Telegram, останавливает
  Windows-задачу, устанавливает webhook, проверяет URL. При ошибке пытается
  вернуть Windows-бота.
- `scripts/verify-cloudflare.py` — проверяет `/health`, адрес webhook,
  отсутствие ошибки доставки и число ожидающих обновлений.
- `scripts/rollback-cloudflare.py` — **ручной аварийный откат**:
  `deleteWebhook` без удаления ожидающих сообщений, включение и запуск
  Windows-задачи. Применять только при реальной проблеме с облаком.

Все операции используют **локальный Python из `.venv`**. Никогда не
запускайте повторный `cutover` для другого бота без проверки имени.
Токен и клиентские базы в публичный репозиторий не попадают.

## Установка с нуля или повторное развёртывание

В папке `cloudflare`:

```powershell
npx wrangler@4.156.0 whoami
npx wrangler@4.156.0 d1 execute atelier-customwear-demo-2026 --remote --file=./schema.sql
npx wrangler@4.156.0 deploy
```

**Не выполняйте `seed.sql` на базе настоящих клиентов**, если не хотите
добавить демонстрационный ассортимент.

Чтобы повторно проверить уже работающий облачный бот:

```powershell
.\.venv\Scripts\python.exe scripts\verify-cloudflare.py
```

Чтобы намеренно вернуть бота на Windows:

```powershell
.\.venv\Scripts\python.exe scripts\rollback-cloudflare.py
```

## Защита от одновременных запросов

После тестирования гонок оформления заказов добавлены следующие проверки:

- Списание **всех** товарных вариантов, запись позиций, очистка корзины и
  запись истории выполняются в одной транзакции D1 `batch()`. При нехватке
  одного товара SQLite `CHECK(stock >= 0)` прерывает весь пакет; нельзя
  списать часть товаров и оставить заказ неоформленным.
- Финальное сообщение покупателя использует условное удаление FSM-сессии:
  только один одновременный запрос может завершить заказ либо заявку.
- Смета отправляется клиенту только если условное обновление по
  `quote_revision` и статусу реально изменило одну запись. Устаревшие
  предложения не отправляются.

Все три случая воспроизведены тестами **до исправлений** (они падали) и
перепроверены после исправлений (успешно).

**Атомарность заказов:** создание заголовка каталожного заказа, резервирование
всех вариантов, записи позиций, очистка корзины и ключ идемпотентности
теперь выполняются в **одном D1 `batch()`**. Аналогично, заголовок
индивидуального пошива и его ключ создаются атомарно. Отмена до отправки
и восстановление остатков происходят в SQLite-триггере одной операции,
а после отправки склад пополняется только отдельным актом физического возврата.

До реальных продаж по-прежнему необходимы испытание этих гарантий на
**отдельной облачной D1**, независимая копия с восстановлением,
действующий продавец и проверка настоящего покупателя в мобильном Telegram.

База D1 поддерживает встроенный Time Travel. На бесплатном тарифе
Cloudflare хранит историю изменений для восстановления за последние
7 дней (не заменяет независимую долгосрочную копию).
Документация: https://developers.cloudflare.com/d1/reference/time-travel/

## Mini App, бизнес-панель и настройка реального ассортимента

Сайт содержит `/app` (витрина), `/admin` (панель),
`/privacy` (сведения о демонстрации и данных), а также API:
- `GET /api/catalog` — публичный демонстрационный каталог;
- `GET /api/me` — проверка подписанного Telegram initData;
- `GET /api/cart`, `POST /api/cart`, `POST /api/checkout` —
  демо-корзина и идемпотентное оформление;
- `POST /api/custom` — индивидуальная заявка;
- `GET /api/admin/dashboard`, `POST /api/admin/product`,
  `POST /api/admin/variant`, `POST /api/admin/order/status`,
  `POST /api/admin/quote`, `POST /api/admin/settings`,
  `POST /api/admin/order/return` —
  только Telegram-администратор, HMAC initData.
- `GET /media/product/ID` — серверное получение фотографии
  из Telegram с ограничением размера и типа файла; BotFather токен
  не выдаётся браузеру.

Кнопка Mini App настроена через Bot API `setChatMenuButton`;
дополнительно /start предлагает кнопку витрины. Для загрузки
фотографии из административного интерфейса используется Telegram deep link
`/start photo_ID` или команда `/photo ID`.

Схема: `migrations/0001_order_status_triggers.sql` —
атомарная отмена с возвратом остатков и история;
`0002_miniapp.sql` — ключи идемпотентности и фото-референсы;
`0003_store_readiness.sql` — данные продавца (по умолчанию пустые),
`0004_shipped_return.sql` — защита от ложного пополнения склада
после отправки и отдельные акты физического возврата.
Миграции применены к облачной базе с сохранением прежних данных.

**Два независимых разрешения:** пока
`DEMO_MODE=1`, `STORE_READY=0`. Нельзя публично принимать реальные
заказы, не настроив данные бизнеса и не проведя отдельную приёмку.
`/payment` не принимает деньги: это исключительно ручные записи.

Запускается ежедневное событие Cloudflare Cron `15 2 * * *` UTC:
удаляются технические ID обработанных обновлений старше 14 суток,
сессии старше 30 суток, ключи повторных запросов старше 90 суток.
История заказов от этого не удаляется.

[Полный контрольный список готовности к продажам](../docs/production-readiness.md).

## Проверки и ограничения

- Облачный интеграционный тест: `node --test cloudflare/test/integration.test.mjs`
  на Node 24. Проверяет каталог, заказ, отмену, возврат остатков, защиту
  от повторной доставки, устаревшую смету и XLSX.
- Настоящий файл XLSX открыт через `openpyxl`, текст формулы не выполняется.
- `/webhook` без секрета возвращает HTTP 403.
- GitHub Actions для Worker и Python прошли.

**Для боевых продаж ещё не готово:** требуется настоящий каталог,
правила обработки персональных данных, испытания с отдельным покупателем,
проверка конкурентного оформления, политика резервного копирования D1
и отключение `DEMO_MODE` только после этих шагов. Банковские платежи
не подключены; записи о поступлениях — ручной учёт.
