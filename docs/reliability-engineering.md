# Контур непрерывной надёжности ателье

**Цель:** не заявлять «багов нет», а удерживать известные критические дефекты вне релизов, систематически расширять исследованные состояния и быстро восстанавливаться после новых сбоев.

## Почему нулевое количество багов недостижимо как доказательство

Число состояний системы неограниченно практически: конкурентные запросы, последовательности покупок, неожиданные входные данные, ошибки Telegram/D1 и изменения инфраструктуры. Конечный набор положительных тестов подтверждает только проверенные трассы. «35/35 успешно» **не означает** «в коде нет дефектов». Даже полный охват строк не подтверждает корректность требований.

Используем **defense in depth** — независимые проверки разных классов отказов, воспроизводимый поиск контрпримеров, обязательную обратную связь и ограничение реальных последствий. Это не математическое доказательство идеальности, но измеримая инженерная система.

## Внедрено в коде

### 1. Инварианты (то, что не должно нарушаться)

Файл: [`cloudflare/test/reliability.test.mjs`](../cloudflare/test/reliability.test.mjs).

- Склад не должен принимать отрицательные остатки.
- Корзины и каталожные заказы связаны только с собственным Telegram-пользователем.
- Оформленный заказ имеет согласованные строки, цену, итог и историю.
- Один ключ повтора создаёт не более одного заказа, независимо от повторов запроса.
- Отмена нового заказа возвращает на склад **ровно** зарезервированные позиции, повторная отмена не срабатывает.
- Архивная позиция не добавляется в корзину и не оформляется, но уже добавленную можно удалить.
- Связи таблиц проходят `PRAGMA foreign_key_check`.

Для каждой последовательности создаётся **отдельная SQLite БД в памяти**, в неё загружаются реальные схема, seed и миграции D1; действия выполняются через **настоящий** `handleApi` с синтетической подписанной Telegram-авторизацией. Независимая JS-модель вычисляет ожидаемые остатки, корзины и суммы. Это тестирование на основе модели (model-based testing), а не повторение того же SQL в тесте.

Генератор псевдослучайных чисел использует фиксированный seed, поэтому любую ошибку можно повторить:

```bash
RELIABILITY_SEED=26011001 RELIABILITY_CASES=1 RELIABILITY_STEPS=90 \
  node --test cloudflare/test/reliability.test.mjs
```

При ошибке сообщение содержит исходный seed и последние действия. Запуски тестируют и самого проверяющего: в отдельной БД намеренно нарушаются остаток и внешний ключ, тест **обязан** зафиксировать нарушение.

**Ограничение:** тест не исчерпывает все интервалы конкурентных запросов и не подменяет настоящую Cloudflare D1. Гонки, которые уже обнаруживались ранее, покрыты отдельными регрессионными сценариями со специально управляемыми прерываниями `DB.batch`.

### 2. Негативные тесты и защита входных данных

- `cloudflare/test/input-boundary.test.mjs`: некорректные JSON-тела — HTTP 400; заявленное или фактическое превышение **16 КиБ** — HTTP 413; никаких необработанных исключений с HTTP 500 для этих клиентских ошибок.
- `safeBody` в `cloudflare/src/api.js` учитывает **фактическое** число байт при чтении потока, а не только заголовок Content-Length. Динамические цены, адреса, тексты и персональные поля уже ограничены в серверных методах.
- Предыдущие тесты проверяют атомарность создания заказов, сохранность данных при D1-откате, конкурентные добавления, возвраты, отмены, фотографии, отчёты Excel и удаление контактов.

### 3. Облачная автоматизация

Файл: [`.github/workflows/reliability.yml`](../.github/workflows/reliability.yml).

| Событие | Проверки |
|---|---|
| Каждый PR | Полный Node-набор, 32 случайных сценария × 100 действий, самотест инвариантов, синтаксис, сохранность `DEMO_MODE=1` и `STORE_READY=0` в конфигурации |
| Push в `main` | Тот же контур на итоговом коммите |
| Ежедневно, GitHub Actions | **Новые** воспроизводимые seed на каждом запуске: 120 сценариев × 150 действий = **18 000 действий** плюс регрессионный набор |
| Ручной `workflow_dispatch` | Повторный прогон при расследовании |

GitHub Actions могут запускать задания по расписанию с задержкой. При провале ежедневного запуска отдельная задача создаёт **один** открытый GitHub issue «[Reliability] Scheduled check failed», а в последующие дни добавляет туда ссылки на новые сбои (если права issues:write доступны). Она не маскирует ошибку, не исправляет её автоматически и не разрешает релиз. Запуск **не равен** непрерывному SLA-мониторингу.

### 4. Регламент выпуска

**Не объединять и не разворачивать PR**, если хотя бы один релевантный тест упал, если остался воспроизводимый P0/P1, или если нет возможности восстановить предыдущую версию и данные. Каждый найденный дефект должен получить: (1) краткую воспроизводимую трассу; (2) тест, падающий до исправления; (3) минимально достаточный патч; (4) повторные проверки; (5) краткую запись в журнале.

Для строгой технической защиты `main` следует активировать GitHub Branch protection / Ruleset и указать обязательными конкретные статусы: `Reliability gate / Seeded state-machine / mutation detection`, `Reliability gate / Full Node regression and fault injection`, `Tests`, `Cloudflare Worker checks`, `Mini App visual acceptance`. Названия следует сверить с актуальными checks в UI. **Само наличие workflow без ruleset не блокирует ручное объединение**.

## Контроль релизов и сохранности сервиса

1. **Демо-ограничения остаются включены.** Рабочие продажи не открываются одной кодовой правкой.
2. **Деплой не связан автоматически с merge.** Отдельная ручная операция: перед ней нужна независимая резервная копия D1 и возможность отката Worker.
3. После деплоя проверяются `/health` (действительный `SELECT 1` к D1), публичный каталог, безавторизационные отказы и сценарии реальной Telegram WebView. Долгие/fuzz-тесты выполняются **только в изолированной БД**, не по действующему публичному API.
4. При сбое: остановить выкладку, сохранить seed/трассу и CI-артефакт, вернуться на проверенный релиз, исправить, добавить регрессию, повторить проверки.

## Остаточные риски

- Не проверена восстановимость D1 из независимого переносимого бэкапа на отдельной облачной базе.
- Нет подтверждённых ограничений частоты запросов (Cloudflare WAF/rate limiting) и лимитов Telegram file-proxy; размер входного JSON — только одна из нескольких границ.
- Telegram API-уведомления после успешно записанного заказа ещё не доставляются через устойчивую очередь/outbox с гарантированными повторными попытками.
- 18 000 последовательных действий не заменяют параллельную нагрузочную проверку в изолированной настоящей D1 и полную мобильную приёмку.
- GitHub branch protection должна быть включена в настройках репозитория, если соответствующие права недоступны подключённому GitHub-инструменту.

## Измеряемые показатели

- Известные воспроизводимые P0/P1, допущенные в релиз: **0 (условие, а не прогноз)**.
- Успешные последние прогоны полного набора и генеративной проверки: **обязательны перед merge**.
- Дефекты, повторно возникшие после исправления: отдельный счётчик regression escapes, каждый увеличивает набор тестов.
- Время обнаружения, локализации и восстановления измерять по CI-логам и журналу инцидентов; не выдумывать заранее проценты сокращения ошибок.

Таким образом, результат — не волшебное «отсутствие багов», а система, которая **не забывает найденные ошибки, регулярно ищет новые и ограничивает возможный ущерб**.
