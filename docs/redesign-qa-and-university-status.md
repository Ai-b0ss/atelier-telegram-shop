# Editorial Atelier v2 — проверка редизайна и техническая приёмка

Дата: **1 ноября 2026 года**. Проект НИТУ МИСИС «Автоматизация продажи авторской одежды через Telegram».

## Контрольная версия и изоляция изменений

- Замороженный коммит: **5b3ac9ac71693cd60ba4889a12de8af7d6ee9919**, ветка **baseline/2026-11-01-stable-demo**.
- Изменения дизайна: отдельная ветка **feature/editorial-atelier-v2**, отдельный Git worktree.
- Опубликованный Cloudflare Worker и D1 **не изменялись** в ходе редизайна.
- DEMO_MODE=1 и STORE_READY=0 остаются обязательным ограничением для рабочего демо. Реальные заказы и банковские платежи не включались.

## Принятое дизайн-решение

Сравнивались три направления: Editorial Atelier (визуальная идентичность), Fashion Archive (экспрессивный тёмный интерфейс), Minimal Commerce (максимально простая покупка). Для прототипа выбран **Editorial Atelier с компактными мобильными карточками Minimal Commerce**.

Работа выполнена непосредственно в существующей архитектуре HTML/CSS/JS, без перехода на React и без добавления внешнего JavaScript-фреймворка. Новый файл editorial.css подключён поверх существующего CSS. Серверные API и расчёты, схема D1, webhook, авторизация и платежи не менялись.

Улучшения:
- Каталог на малых экранах представлен горизонтальными карточками: название, цена, выбранный размер и кнопка остаются рядом с областью изображения.
- Убрана имитация футболки на первом экране; до появления подлинного снимка выводится честное «Фото готовится», а не чужой товар.
- Единая спокойная цветовая система, более строгая типографика, SVG-иконки и понятная фиксированная навигация с учётом нижнего safe area.
- Цена соответствует выбранному варианту; при исчезновении варианта из доступных выбирается существующий.
- В публичной витрине действие «Посмотреть в Telegram» действительно открывает Telegram-бота вместо ошибочного сообщения.
- Выбранные категории и размеры обозначены атрибутами aria-pressed; интерактивные элементы не меньше 44 px в проверенных состояниях.
- Декоративные эффекты и сторонние фотографии не добавлялись.

## Реальная проверка Telegram Desktop через Windows Bridge

Установлены **три авторизованные учётные записи**, исходящие из одного Telegram Desktop. Проверена версия 7.3.3 x64, использован бот https://t.me/atelier_customwear_2611_bot.

| Роль/аккаунт | Проведено | Реальный результат |
|---|---|---|
| Основной администратор | /start, /orders, /stats, /report | Команды обработаны; пришёл atelier-cloud-report.xlsx (~8,7 КБ); в проверенный момент заказов 0, показатели 0 |
| Основной администратор | каталог → категория → сумка-шоппер → one size / молочный | Бот сообщил «Изделие добавлено», предложил открыть корзину |
| Дополнительный аккаунт A | /start, /admin, /orders | Ответ «Магазин пока в тестовом режиме. Реальные заказы не принимаются»; приватные заказы не показаны |
| Дополнительный аккаунт B | /start, /orders | Аналогичное ограничение демо-режима; приватные заказы не показаны |

**Важно:** демо-защита допускает полноценные действия покупателя только для администратора; поэтому два реальных неадминистратора сейчас подтверждают отказ в доступе, но **не** самостоятельную сквозную покупку. Отправка заказа, его отмена с проверкой остатков и физический возврат после отгрузки на трёх реальных аккаунтах не проверены. Испытания пришлось остановить, когда другой агент начал работу с тем же Telegram Desktop; конфликты ввода исключены завершением нашего режима доступа.

Микробенчмарк SQL (исторически 0,795 с на 50 сценариев) нельзя выдавать за время оформления человеком или процент экономии труда. Для количественной эффективности нужно провести сопоставимый хронометраж 10 ручных и 10 автоматизированных заказов по одной методике.

## Открытые условия перед публикацией/реальными продажами

1. Проверить новое оформление в **настоящем Telegram WebView на Android/iOS** и многопользовательскую корзину/отмену на изолированной тестовой базе.
2. Добавить реальные фотографии, размеры, описания, сроки и цены только после согласования с автором ассортимента.
3. Подготовить юридические условия, возвраты, контакты и реальный порядок оплаты; не переключать боевые флаги ради демонстрации.
4. Организовать независимо восстанавливаемые резервные копии D1 и провести восстановление; текущая DPAPI-копия привязана к Windows-пользователю.
5. Замерить эффективность ручного и автоматического процесса, а не приписывать синтетическим тестам бизнес-экономию.

**Решение для интеграции:** сначала PR с документированными снимками и успешными тестами; production/demo Worker оставить без изменений до подтверждённой финальной приёмки.


## Облачные проверки и следующий этап (01.11.2026)

После первоначальной локальной проверки в draft PR №5 добавлены две независимые проверки GitHub Actions:

1. **Mini App visual acceptance:** `.github/workflows/visual-qa.yml`, `scripts/visual_qa.mjs` и `scripts/editorial_preview.py`. Ubuntu-runner запускает изолированный тестовый HTTP-каталог, отказывает во всех POST с кодом 403 и проходит Chrome DevTools проверку на ширинах 375, 390, 430, 768, 1280 px. Проверяются загрузка данных, фильтр категории, переход в бот, размеры кнопок (не меньше 44 px), горизонтальное переполнение, JavaScript-исключения и переключение «каталог → корзина → каталог», включая скрытие декоративного первого экрана. Снимки и JSON-отчёт выгружаются в артефакты CI. Реальная Cloudflare D1 при этом **не используется**.
2. **Live demo health (read-only):** `.github/workflows/live-demo-health.yml` и `scripts/check_cloud_demo.py`. Без токенов и без POST по HTTPS читаются `/health`, `/api/catalog`, `/app`, `/privacy` и три закрытых API без авторизации. По факту успешного запуска подтверждены HTTP 200, наличие трёх товаров/четырёх вариантов, режим demo, доступность D1 через каталог, защитный CSP и отказ анонимному доступу к личным и административным маршрутам (3/3). Это проверка доступности и границ доступа, **не** доказательство полноценной покупки.

В интерфейсе дополнительно реализовано отключение повторного быстрого нажатия на добавление в корзину, а при открытии корзины, индивидуального пошива и админки первый декоративный экран скрывается.

**Режим эксплуатации:** PR остаётся draft. Расписание ежедневной проверки демо (06:23 UTC) прописано в workflow, но GitHub запускает `schedule` только с ветки по умолчанию; **до принятия PR это расписание не активно**. Сборки этой ветки не выполняют деплой и не изменяют данные D1.

Открытые условия остались прежними: независимая реальная Telegram WebView-приёмка на iOS/Android и сквозной заказ/отмена, восстановление независимой резервной копии, настоящие материалы ателье, доказательный замер времени менеджера.
